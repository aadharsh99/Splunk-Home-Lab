# Splunk SOC Home Lab — Threat Detection & Investigation

![SOC](https://img.shields.io/badge/Focus-SOC%20%7C%20Detection%20%7C%20Investigation-blue) ![MITRE](https://img.shields.io/badge/MITRE%20ATT%26CK-mapped-orange) ![Splunk](https://img.shields.io/badge/SIEM-Splunk-black)

> A SOC portfolio lab demonstrating reconnaissance, SMB enumeration and suspicious command execution against a Windows/IIS target, with Suricata, IIS, Windows Event Logs and Sysmon telemetry analysed in Splunk and detections forwarded to DFIR-IRIS.

[![Architecture](./architecture/splunk-soc-lab-architecture.png)](architecture/splunk-soc-lab-architecture.png)

## Overview

This project demonstrates a security-operations workflow from activity generation through telemetry, detection, investigation and case management:

`Authorised activity → telemetry → Splunk → detection → alert → DFIR-IRIS case → analyst investigation → resolution`

The four telemetry sources ingested into Splunk are **Suricata, IIS, Windows Event Logs and Sysmon**. Splunk is the SIEM/analysis platform, while DFIR-IRIS is used for case management.

See [`SETUP.md`](./SETUP.md) for the reproduction and integration procedure.

## Lab Scenarios

| Scenario | Telemetry | Detection / Investigation | MITRE ATT&CK |
|---|---|---|---|
| Nmap reconnaissance against Windows/IIS | Network telemetry + IIS HTTP requests | Reconnaissance investigation | T1046 — Network Service Scanning |
| SMB enumeration | Windows Security Event ID 4624 + network context | Scheduled Splunk detection and alert | T1135 — Network Share Discovery |
| Suspicious `whoami /all` execution | Sysmon Event ID 1 | Process investigation and scheduled detection | T1033 — System Owner/User Discovery |

The captured `whoami.exe` process is the direct evidence; the process tree shows `cmd.exe` as the parent.

## Telemetry Sources

| Data source | Evidence / telemetry | Investigation purpose |
|---|---|---|
| **Suricata** | Network flow / protocol telemetry | Network-level visibility into reconnaissance and connections |
| **IIS** | IIS HTTP access logs | Application-level visibility into requests reaching the web server |
| **Windows Event Logs** | Windows Security events, including Event ID 4624 | Authentication and network-logon evidence |
| **Sysmon** | Sysmon Event ID 1 and related endpoint telemetry | Process creation, command line and parent-process investigation |

**Splunk Enterprise is the analysis platform, not a telemetry source.** The Splunk Universal Forwarder is the collection/forwarding mechanism and is not counted as a telemetry source. DFIR-IRIS is also not a telemetry source.

## Detection Engineering

Two scheduled detections are documented in [`docs/DETECTION-RULES.md`](./docs/DETECTION-RULES.md):

- **SMB Enumeration Detected** — identifies network logons associated with SMB enumeration.
- **Suspicious Whoami Discovery Activity** — detects `whoami.exe /all` discovery activity using Sysmon Event ID 1.

Suricata is documented as a network-sensor component; the available evidence does not claim a Suricata alert for the Nmap scenario.

Each detection includes its purpose, telemetry source, logic, investigation pivots and tuning considerations.

## Investigation Methodology

Each scenario follows the same analyst workflow:

1. Confirm the alert is generated by expected telemetry.
2. Identify source, destination, user and timestamp details.
3. Pivot from the detection to the underlying raw event.
4. Correlate endpoint, network and application evidence.
5. Determine the observed behaviour and likely objective.
6. Map the behaviour to MITRE ATT&CK.
7. Record limitations and recommended next steps.

Detailed case write-ups are in [`docs/INVESTIGATIONS.md`](./docs/INVESTIGATIONS.md).

## DFIR-IRIS Case Management

DFIR-IRIS runs on a separate Debian 13 VM. Splunk detections can be forwarded to the Python webhook bridge, which creates an IRIS alert and escalates it into an IRIS case.

`Splunk Detection → Webhook → Python Bridge → IRIS Alert → IRIS Case → L1 Triage / Investigation → Resolution`

**Case creation is automated; investigation and final resolution are not.** The intended escalation model is `L1 → L2 → L3` when deeper or specialist analysis is required. The lab does not implement automated L1/L2/L3 escalation.

The integration was validated with Splunk-format webhook payloads for the three lab scenarios. This demonstrated successful **webhook → Python bridge → IRIS alert → IRIS case** creation. It does not claim that all three scenarios were simultaneously executed through live Splunk detections in a fully loaded VM stack.

See [`docs/DFIR-IRIS-CASE-MANAGEMENT.md`](./docs/DFIR-IRIS-CASE-MANAGEMENT.md) and [`automation/README.md`](./automation/README.md).

## Architecture

[![Splunk SOC Lab Architecture](./architecture/splunk-soc-lab-architecture.png)](architecture/splunk-soc-lab-architecture.png)

The architecture reflects the actual telemetry model. Suricata, IIS, Windows Event Logs and Sysmon feed Splunk independently. Splunk detections then flow through the webhook bridge into DFIR-IRIS for automated case creation, followed by analyst investigation and resolution.

See [`architecture/README.md`](./architecture/README.md) for the architecture notes.

## Resource Constraints

Due to limited system resources in the home-lab environment, the full VM stack could not be run simultaneously for a live end-to-end Splunk investigation of every scenario. The attack telemetry, Splunk detection evidence and IRIS case workflows were documented using the available lab evidence, while the Splunk-to-IRIS automation was separately validated with Splunk-format webhook payloads.

See [`docs/RESOURCE-CONSTRAINT-NOTE.md`](./docs/RESOURCE-CONSTRAINT-NOTE.md).

## Security & Scope

All activity represented in this repository was performed in an authorised lab environment. Public repository documentation uses obfuscated private IP notation such as `192.168.xxx.xxx` where appropriate.

Do not publish real IRIS API keys, passwords, tokens or unmasked sensitive network information. The bridge configuration template contains placeholders only.
