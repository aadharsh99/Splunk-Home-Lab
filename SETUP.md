# Setup Guide

This document describes how to reproduce the Splunk SOC home lab and its Splunk-to-DFIR-IRIS automation.

The repository is designed around a small authorised lab environment rather than a production deployment.

## 1. Lab Components

| Component | Role |
|---|---|
| Kali Linux | Authorised attacker / test-event source |
| Windows | Target endpoint and IIS server |
| Splunk Enterprise on Ubuntu | SIEM, search, detection and alerting |
| Splunk Universal Forwarder | Log collection and forwarding |
| Suricata | Network telemetry sensor |
| Debian 13 | DFIR-IRIS case-management VM and Python webhook bridge |
| Apache / bWAPP | Web application target used for authorised testing |

The four security telemetry sources ingested into Splunk are:

1. **Suricata** — network telemetry
2. **IIS** — HTTP/web-server logs
3. **Windows Event Logs** — Security/System audit telemetry
4. **Sysmon** — endpoint/process telemetry, including Event ID 1

Splunk is the analysis platform. DFIR-IRIS is the case-management platform and is **not** a telemetry source.

## 2. Network Layout

The lab uses a bridged local network. Public repository documentation intentionally masks addresses as:

```text
192.168.xxx.xxx
```

A representative flow is:

```text
Kali attacker
    |
    v
Windows target / IIS
    |
    +--> Windows Event Logs
    +--> Sysmon
    +--> IIS logs
    +--> Suricata network telemetry
              |
              v
     Splunk Universal Forwarder
              |
              v
      Splunk Enterprise
              |
              v
       Splunk Webhook
              |
              v
 Python Webhook Bridge :5050
              |
              v
        DFIR-IRIS API
              |
              v
          IRIS Case
```

## 3. Prerequisites

Before configuring the repository, have the following available in the lab:

- Proxmox or another hypervisor capable of running the required VMs
- Kali Linux
- Windows endpoint with IIS
- Ubuntu VM running Splunk Enterprise
- Debian 13 VM for DFIR-IRIS and the Python bridge
- Sysmon installed on the Windows endpoint
- Suricata configured on the appropriate network interface
- Splunk Universal Forwarder on the endpoint(s) that send logs to Splunk
- Python 3 and network connectivity between the bridge and DFIR-IRIS

Use only systems and network resources that you own or are explicitly authorised to test.

## 4. Splunk Data Ingestion

Configure the Universal Forwarder and/or relevant Splunk inputs so the four telemetry sources are searchable in Splunk.

At minimum, verify that you can retrieve:

### Windows Event Logs

Windows Security events should be available for investigation, including Event ID `4624` where generated by the lab activity.

### Sysmon

Sysmon Event ID `1` should be searchable for process creation activity. The repository uses the `Image`, `CommandLine`, `ParentImage` and `User` fields during investigation.

### IIS

IIS HTTP access logs should be ingested separately so application-layer activity can be correlated with network and endpoint evidence.

### Suricata

Suricata flow/protocol telemetry should be ingested into Splunk. See [`docs/SURICATA.md`](./docs/SURICATA.md) for the project-specific Suricata documentation.

## 5. Validate Splunk Visibility

Before testing detections, confirm that the expected data is present in Splunk.

Examples:

```spl
index=main whoami.exe
```

```spl
index=main EventCode=4624
```

```spl
index=main
```

Then narrow searches using the fields documented in [`docs/DETECTION-RULES.md`](./docs/DETECTION-RULES.md) and [`docs/INVESTIGATIONS.md`](./docs/INVESTIGATIONS.md).

## 6. Configure DFIR-IRIS

Deploy DFIR-IRIS on the separate Debian 13 VM according to the DFIR-IRIS documentation for your chosen deployment method.

The bridge requires an IRIS API key with permission to create alerts and escalate alerts into cases.

The lab configuration uses these IRIS IDs:

| Setting | Lab value |
|---|---:|
| Customer | `1` |
| Medium severity | `1` |
| Scanning classification | `11` |
| New alert status | `2` |

These values are stored in the bridge implementation and are also shown in the sanitised configuration template.

## 7. Install the Python Webhook Bridge

Run the bridge on the Debian 13 VM used for the IRIS integration.

Create a virtual environment and install the required packages:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install flask requests
```

Copy the environment template:

```bash
cp automation/bridge.env.example automation/bridge.env
```

Edit `automation/bridge.env` and replace the placeholder API key with the private IRIS API key.

Example:

```text
IRIS_URL=https://127.0.0.1
IRIS_API_KEY=YOUR_PRIVATE_IRIS_API_KEY
IRIS_CUSTOMER_ID=1
IRIS_MEDIUM_SEVERITY_ID=1
IRIS_SCANNING_CLASSIFICATION_ID=11
IRIS_ALERT_STATUS_ID=2
```

Do **not** commit `bridge.env` or a real API key to GitHub.

The application listens on TCP port `5050` and exposes:

```text
GET  /health
POST /splunk
```

Start it with:

```bash
source .venv/bin/activate
export $(grep -v '^#' automation/bridge.env | xargs)
python3 automation/splunk_iris_bridge.py
```

Check the health endpoint:

```bash
curl http://127.0.0.1:5050/health
```

Expected response:

```json
{"status":"ok"}
```

## 8. Run the Bridge as a Service

For a persistent lab deployment, create a systemd service for the bridge.

Example service file:

```ini
[Unit]
Description=Splunk to DFIR-IRIS Webhook Bridge
After=network.target

[Service]
Type=simple
WorkingDirectory=/opt/splunk-iris-bridge
EnvironmentFile=/opt/splunk-iris-bridge/automation/bridge.env
ExecStart=/opt/splunk-iris-bridge/.venv/bin/python /opt/splunk-iris-bridge/automation/splunk_iris_bridge.py
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

Then enable and start the service:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now splunk-iris-bridge
sudo systemctl status splunk-iris-bridge
```

The exact filesystem path can be changed to match your deployment.

## 9. Configure the Splunk Webhook

Configure each scheduled detection so that its alert action sends a webhook to the bridge endpoint:

```text
http://<BRIDGE_IP>:5050/splunk
```

The webhook should provide enough metadata for the bridge to identify the detection, including fields such as:

- detection/search name
- SID
- owner
- Splunk app
- results link
- triggering result/event

The bridge maps the received detection to the lab case type:

| Detection | IRIS case | MITRE ATT&CK |
|---|---|---|
| Nmap / reconnaissance | Nmap Reconnaissance Against Windows Server | T1046 |
| SMB / enumeration | SMB Enumeration Against Windows Server | T1135 |
| Other supported discovery event | Suspicious Whoami Discovery Activity | T1033 |

## 10. Test the Integration

The proven workflow is:


## 11. Analyst Workflow

Automatic case creation is not the same as automatic incident resolution.

The implemented workflow is:

```text
Splunk Detection
      -> Automatic IRIS Alert
      -> Automatic IRIS Case Creation
      -> L1 SOC Triage / Investigation
      -> Resolution
```

The analyst should review the underlying telemetry, validate the detection, correlate relevant evidence, record the outcome and then resolve the case when appropriate.

Where additional expertise is required, the intended professional escalation path is:

```text
L1 -> L2 -> L3 (when specialist analysis is required) -> Resolution
```

The lab does not implement an automated L1/L2/L3 escalation mechanism.

## 12. Lab Scenarios

The repository documents three principal scenarios:

### Nmap reconnaissance

Use Nmap from the authorised Kali system against the Windows/IIS target. Review the resulting network telemetry, IIS HTTP requests and Suricata visibility in Splunk.

### SMB enumeration

Perform the authorised SMB enumeration activity from the Kali test system. Review the Windows Security evidence, including Event ID `4624` where generated, and the associated Splunk detection.

### Suspicious `whoami /all`

Run the authorised discovery command:

```cmd
whoami /all
```

Review Sysmon Event ID `1`, including the executable, command line, parent process and user fields, then investigate the corresponding Splunk detection.

Detailed scenario evidence is documented in [`docs/INVESTIGATIONS.md`](./docs/INVESTIGATIONS.md).

## 13. Resource Constraints and Reproduction Limits

The home-lab environment has limited system resources. The project therefore does **not** claim that the complete VM stack was run simultaneously for a live end-to-end Splunk investigation of every scenario.

The attack evidence, Splunk detection evidence and IRIS case workflows were documented using the available lab evidence, while the Splunk-to-IRIS automation was separately validated with Splunk-format webhook payloads.

This distinction should be preserved when presenting or extending the project.

## 14. Security Notes

The bridge currently uses `requests` with certificate verification disabled (`verify=False`) because the lab uses an HTTPS IRIS endpoint where certificate validation was not part of the home-lab integration test.

Do not copy the configuration into a production environment without reviewing TLS validation, authentication, network access controls, secrets handling and service hardening.

Never publish:

- real IRIS API keys
- passwords
- private tokens
- unmasked public IP addresses
- credentials stored in screenshots
